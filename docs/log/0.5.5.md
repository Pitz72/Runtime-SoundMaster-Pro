## Fix M1 — Double import dinamico e type unsafe in `CleanerModule.tsx`

### File interessati

- `src/components/modules/CleanerModule.tsx` — handler `handleNcQuarantine` e `handleDupResolve`

### Descrizione del problema

In due handler (`handleNcQuarantine` riga 259, `handleDupResolve` riga 332), il codice eseguiva un dynamic import di `invoke` già disponibile come import statico in cima al file:

```tsx
// In cima al file (riga 3) — invoke già importato staticamente:
import { invoke } from '@tauri-apps/api/core';

// ... 250 righe dopo, dentro l'handler (bug):
const { invoke: inv } = await import('@tauri-apps/api/core');  // ridondante
try {
    const stats = await inv('get_library_stats');  // non tipato
    setLibraryStats(stats as any);                 // type cast non sicuro
} catch { /* non bloccante */ }
```

Il dynamic import non causava errori runtime perché il bundler (Vite) deduplica il modulo, ma presentava due problemi distinti:

1. **Ridondanza anomala**: il codice segnalava una svista — l'import statico in cima al file era stato ignorato. Un futuro manutentore potrebbe non capire perché `invoke` viene reimportato dinamicamente.

2. **Type unsafe**: `await inv('get_library_stats')` restituisce `unknown` (nessun tipo generico), e il cast `stats as any` bypassava completamente il type system TypeScript. Se la firma del comando Rust cambiasse, TypeScript non avvertirebbe. Il pattern corretto — usato in `App.tsx` e in tutti gli altri handler dello stesso componente — è `invoke<LibraryStats>('get_library_stats')`.

Inoltre `LibraryStats` non era incluso nell'import dei tipi dal modulo store, rendendo impossibile usare `invoke<LibraryStats>` senza aggiungerlo prima.

### Fix applicato

**1. Aggiunto `LibraryStats` all'import dei tipi:**

```tsx
// PRIMA:
import type {
  CleanerResult, QuarantineResult, ScanResult,
  DuplicateDetectResult, DuplicateGroup, DuplicateResolveResult,
} from '../../store/appStore';

// DOPO:
import type {
  LibraryStats,
  CleanerResult, QuarantineResult, ScanResult,
  DuplicateDetectResult, DuplicateGroup, DuplicateResolveResult,
} from '../../store/appStore';
```

**2. Rimossi i dynamic import, sostituiti con l'invoke statico tipato (×2):**

```tsx
// PRIMA (in handleNcQuarantine e handleDupResolve — identici):
const { invoke: inv } = await import('@tauri-apps/api/core');
try {
    const stats = await inv('get_library_stats');
    setLibraryStats(stats as any);
} catch { /* non bloccante */ }

// DOPO:
try {
    const stats = await invoke<LibraryStats>('get_library_stats');
    setLibraryStats(stats);
} catch { /* non bloccante — le stats vengono aggiornate al prossimo avvio */ }
```

### Impatto del fix

- `setLibraryStats` riceve ora un oggetto `LibraryStats` tipato correttamente — TypeScript segnala errori se la struttura cambia
- Nessun dynamic import inutile
- Pattern coerente con `App.tsx` e con gli altri `invoke<T>` nel componente

## Fix M2 — Scanner accumula `Vec<PathBuf>` in RAM (two-pass refactor)

### File interessati

- `src-tauri/src/scanner.rs` — funzione `scan_workspace_impl`

### Descrizione del problema

La versione precedente dello scanner accumulava tutti i `PathBuf` dei file audio in un `Vec<PathBuf>` prima di iniziare l'indicizzazione nel DB:

```rust
// PRIMA (bug architetturale):
let audio_files: Vec<PathBuf> = WalkDir::new(&workspace_path)
    .follow_links(true)
    .into_iter()
    .filter_map(|entry| entry.ok())
    .filter(|entry| /* ... */)
    .map(|entry| entry.into_path())
    .collect();  // ← TUTTI i PathBuf in RAM simultaneamente

let total = audio_files.len() as u64;

for (i, path) in audio_files.iter().enumerate() {
    // INSERT file per file...
}
```

Questo contraddiceva esplicitamente la specifica in `PROGETTO/PIANIFICAZIONE.md §4`:

> *"Scansione stream-chunked / async per non saturare la RAM (architettura DB-First: ogni file trovato viene scritto su SQLite, **non accumulato in RAM**)"*

**Impatto concreto sul consumo di memoria:**

| Dimensione libreria | PathBuf medi | RAM occupata (stima) |
| --- | --- | --- |
| 10.000 file | ~100 bytes × 10k | ~1 MB (trascurabile) |
| 100.000 file | ~100 bytes × 100k | ~10 MB (fastidioso) |
| 500.000 file (target) | ~100 bytes × 500k | ~50 MB (problematico) |

Su una macchina che esegue anche RadioDJ, MB Studio o Azuracast in background (target principale dell'utenza), 50 MB extra durante la scansione è un impatto reale.

### Soluzione: approccio two-pass

Il problema principale del singolo-pass era: per mostrare la barra di progresso con percentuale corretta, il frontend ha bisogno del campo `total` (totale file) dal primo evento. Questo richiedeva di sapere quanti file ci sono prima di iniziare a scrivere — da qui il `collect()`.

**Two-pass solution:**

- **Pass 1 — Conteggio puro**: WalkDir traversal con solo un contatore, nessun alloc di PathBuf. Restituisce `total: u64`.
- **Pass 2 — Indicizzazione diretta**: WalkDir di nuovo, INSERT ogni file appena trovato. Max 1 `DirEntry` in memoria alla volta — O(1) RAM indipendente da n.

```rust
// DOPO — Pass 1: conta senza allocare
let total = WalkDir::new(&workspace_path)
    .follow_links(true)
    .into_iter()
    .filter_map(|e| e.ok())
    .filter(|e| is_audio_file(e))
    .count() as u64;

// DOPO — Pass 2: processa file per file, nessun Vec
let mut scanned = 0u64;
for entry in WalkDir::new(&workspace_path)
    .follow_links(true)
    .into_iter()
    .filter_map(|e| e.ok())
    .filter(|e| is_audio_file(e))
{
    scanned += 1;
    let path = entry.path();
    // INSERT direttamente — nessun accumulo
    stmt.execute(params![path_str, filename, format, file_size, scan_id]).ok();
    // emit progress ogni 100 file...
}
```

Il filtro `is_audio_file` è una closure definita una sola volta e riusata in entrambi i pass, evitando duplicazione della logica di filtro.

### Tradeoff consapevole: doppia traversata filesystem

Il filesystem viene attraversato due volte invece di una. Su sistemi con:
- **Page cache OS attiva** (scenario normale per Windows): il secondo pass è quasi gratuito — le directory sono già in cache dal primo.
- **Filesystem lento o NAS remoto**: il secondo pass aggiunge latenza. Tuttavia, l'indicizzazione SQLite stessa è il collo di bottiglia dominante, non la traversata directory.

Il guadagno di memoria costante O(1) giustifica il costo del secondo pass, specialmente sul target d'uso (macchine con RadioDJ/MB Studio in background).

### Nessuna modifica alla firma pubblica

`scan_workspace` (comando Tauri), `ScanProgress`, `ScanResult` — invariati. Il frontend non richiede aggiornamenti.

## Fix M3 — JSON parsing FFprobe con `serde_json` (sostituisce string matching)

### File interessati

- `src-tauri/src/cleaner.rs` — funzione `probe_file`, rimossa `extract_duration_from_json`

### Descrizione del problema

La versione precedente di `probe_file` usava string matching per estrarre informazioni dal JSON di FFprobe:

```rust
// PRIMA — fragile, dipende dalla formattazione esatta del JSON:
let has_video = json.contains(r#""codec_type": "video""#)
    || json.contains(r#""codec_type":"video""#);

// Extract duration — stringa cercata manualmente nel JSON:
fn extract_duration_from_json(json: &str) -> Option<f64> {
    let pos = json.find("\"duration\"")?;
    // parsing manuale carattere per carattere...
}
```

**Problemi documentati:**

1. **`has_video`**: copriva solo due varianti di spaziatura (`": "` e `":"`). Non gestiva `" : "` (spazio prima del colon), formattazione multi-riga con indent o altri stili. Sebbene FFprobe 8.1 usi sempre `"codec_type": "video"` (con spazio), questo accoppiava il codice a un dettaglio implementativo di una specifica versione.

2. **`extract_duration_from_json`**: cercava la prima occorrenza di `"duration"` nel JSON grezzo. Il JSON FFprobe può avere `"duration"` sia in `streams[i]` che in `format`. La funzione restituiva la prima trovata, che nel JSON è tipicamente uno stream (audio principale), non il container. Alcuni formati riportano duration diversa nello stream e nel format (es. AAC in ADTS): prendere lo stream anziché il format potrebbe restituire una durata leggermente inaccurata.

3. **Manutenibilità**: il parsing manuale è fragile per future versioni di FFprobe che potrebbero cambiare la formattazione del JSON.

`serde_json` era già dichiarato in `Cargo.toml` ma non usato in `cleaner.rs`.

### Fix applicato

**Aggiunta di struct `Deserialize` private per il parsing tipizzato:**

```rust
#[derive(serde::Deserialize)]
struct FfprobeOutput {
    streams: Option<Vec<FfprobeStream>>,
    format: Option<FfprobeFormat>,
}

#[derive(serde::Deserialize)]
struct FfprobeStream {
    codec_type: Option<String>,
    duration: Option<String>,  // FFprobe restituisce duration come stringa
}

#[derive(serde::Deserialize)]
struct FfprobeFormat {
    duration: Option<String>,
}
```

`serde_json` con `#[derive(Deserialize)]` ignora automaticamente tutti i campi non dichiarati nelle struct — non è necessario mappare l'intero schema FFprobe.

**Riscrittura di `probe_file` con parsing tipizzato:**

```rust
Ok(out) => {
    let json_str = String::from_utf8_lossy(&out.stdout);
    let parsed: FfprobeOutput = match serde_json::from_str(&json_str) {
        Ok(p) => p,
        Err(_) => return (false, None, None), // JSON inatteso — conservativo
    };

    // has_video: serde gestisce tutte le varianti di formattazione
    let has_video = parsed.streams.as_ref().map_or(false, |streams| {
        streams.iter().any(|s| s.codec_type.as_deref() == Some("video"))
    });

    // duration: prima dal container format (più affidabile),
    // poi dal primo stream come fallback (formati senza container duration)
    let duration = parsed.format
        .as_ref()
        .and_then(|f| f.duration.as_deref())
        .and_then(|d| d.parse::<f64>().ok())
        .or_else(|| {
            parsed.streams.as_ref().and_then(|streams| {
                streams.iter()
                    .filter_map(|s| s.duration.as_deref().and_then(|d| d.parse::<f64>().ok()))
                    .next()
            })
        });

    (has_video, duration, None)
}
```

**Rimossa `extract_duration_from_json`** — non più necessaria. La logica è integrata direttamente in `probe_file` tramite le struct serde.

### Miglioramento aggiuntivo: fallback duration stream→format

La nuova implementazione cerca la duration **prima in `format.duration`** (durata totale del container, la più affidabile), con **fallback al primo `stream.duration`** trovato. Questo gestisce correttamente:

- File MP3, FLAC, WAV standard: duration in `format`
- File AAC raw (ADTS), MP3 senza header ID3v2: duration solo negli stream
- File con video stream (es. `.mp4` mascherato da `.mp3`): duration nel format container, `has_video = true`

### Impatto del fix

- `has_video` rilevato correttamente su qualsiasi formattazione del JSON FFprobe
- `duration` estratta dall'origine più affidabile (format container → stream fallback)
- Manutenibilità: aggiornamenti futuri di FFprobe non rompono il parsing
- Codice più leggibile e testabile per tipo invece di parsing manuale
