## Contesto

Il primo test reale su una libreria di produzione ha rilevato due problemi:

1. **98% dei file flaggati come non-conformi** con categoria `video_stream` — risultato chiaramente impossibile su una libreria radio reale. La causa era un falso positivo sistematico nella detection dei video stream via FFprobe.

Analisi eseguita grazie al file di log introdotto in v0.5.7, che ha permesso di identificare immediatamente che tutti i file venivano flaggati come `video_stream`.

## Fix 1 — Cover Art FFprobe: falso positivo `video_stream` su tutti gli MP3 con copertina

### File interessati

- `src-tauri/src/cleaner.rs` — struct `FfprobeStream`, logica `has_video` in `probe_file`

### Causa radice

Quasi tutti gli MP3 moderni hanno la **copertina dell'album incorporata nel file** come tag ID3 di tipo `APIC` (Attached Picture). FFprobe riporta questa copertina come uno stream con `codec_type = "video"` — tecnicamente corretto, perché è un'immagine JPEG/PNG codificata nel container.

Il codice precedente interpretava qualsiasi stream con `codec_type = "video"` come un file video mascherato da audio:

```rust
// PRIMA — falso positivo su TUTTI gli MP3 con copertina:
let has_video = parsed.streams.as_ref().map_or(false, |streams| {
    streams.iter().any(|s| s.codec_type.as_deref() == Some("video"))
});
// Risultato test reale: 36.198 / 36.701 file flaggati (98%)
```

### La distinzione corretta: `disposition.attached_pic`

FFprobe include nei metadati di ogni stream un oggetto `disposition` con flag booleani. Il flag `attached_pic = 1` indica esplicitamente che lo stream è una copertina allegata (cover art), non un video reale:

```json
"streams": [{
    "codec_type": "video",
    "codec_name": "mjpeg",
    "disposition": {
        "attached_pic": 1,   ← copertina album — da ignorare
        ...
    }
}]
```

Un file video reale mascherato da MP3 avrebbe `attached_pic = 0` (o il campo assente).

### Fix applicato

**Aggiunta struct `FfprobeDisposition`**:

```rust
#[derive(serde::Deserialize)]
struct FfprobeDisposition {
    attached_pic: Option<u8>,
}
```

**Aggiunto campo `disposition` a `FfprobeStream`**:

```rust
#[derive(serde::Deserialize)]
struct FfprobeStream {
    codec_type: Option<String>,
    duration: Option<String>,
    disposition: Option<FfprobeDisposition>,  // ← aggiunto
}
```

**Condizione `has_video` aggiornata**:

```rust
// DOPO — esclude esplicitamente la cover art:
let has_video = parsed.streams.as_ref().map_or(false, |streams| {
    streams.iter().any(|s| {
        s.codec_type.as_deref() == Some("video")
            && s.disposition
                .as_ref()
                .and_then(|d| d.attached_pic)
                .unwrap_or(0)  // campo assente → tratta come 0 (conservativo)
                != 1           // 1 = cover art, da ignorare
    })
});
```

**Logica della condizione:**
- `codec_type = "video"` AND `attached_pic != 1` → vera video stream → NON CONFORME
- `codec_type = "video"` AND `attached_pic == 1` → copertina album → IGNORARE
- `codec_type = "video"` AND `disposition` assente → `attached_pic` trattato come 0 → conservativo, segnala

### Confronto con TuneUp (riferimento originale)

TuneUp v3.0.2 non esegue il check FFprobe video stream — usa solo pattern sul filename. Il nostro approccio è più completo (rileva video reali nascosti da MP3 senza pattern nel nome), ma richiedeva questo fix per non fare falsi positivi sulla copertina.

### Impatto atteso

Su una libreria radio normale: da 98% falsi positivi → risultato corretto. I soli file che riceveranno `video_stream` saranno MP3/WAV che contengono effettivamente stream video (es. file scaricati da YouTube come audio ma il container contiene anche video, senza cover art).

## Fix 2 — UX: progress bar scansione workspace nel Cleaner

### File interessati

- `src/components/modules/CleanerModule.tsx` — Step 1 mode Non-Conform e Step 1 mode Duplicates

### Problema

Durante la scansione del workspace (che può durare 30-150 secondi su drive lenti o librerie grandi), il bottone "Start Non-Conform Analysis" era grigio con testo "Scanning workspace..." ma non c'era alcun indicatore visivo di cosa stesse succedendo o quanto mancasse.

L'utente vedeva un bottone grigio senza capire se l'app era bloccata o stava lavorando. Cliccando i bottoni "Non-Conform" / "Duplicates" (sempre attivi, cambiano solo la vista), la scansione sembrava "sbloccarsi" — ma era solo coincidenza con il termine naturale della scansione.

Il problema era che `scanProgress` (disponibile nello Zustand store e già usato nell'HubModule) non veniva importato in `CleanerModule`.

### Fix applicato

Aggiunto `scanProgress` all'import dello store in `CleanerModule`:

```tsx
const { ..., isScanning, setIsScanning, scanProgress, ... } = useAppStore();
```

Aggiunta progress bar animata in **entrambi gli Step 1** (Non-Conform e Duplicates), visibile solo quando `isScanning && scanProgress`:

```tsx
{isScanning && scanProgress && (
  <div className="w-full max-w-md mb-4 space-y-2">
    <div className="flex justify-between font-mono text-[9px] text-industrial-amber uppercase">
      <span>Workspace scan in progress — please wait</span>
      <span>
        {scanProgress.total > 0
          ? `${scanProgress.scanned.toLocaleString()} / ${scanProgress.total.toLocaleString()}`
          : 'Discovering...'}
      </span>
    </div>
    <div className="h-0.5 bg-industrial-border w-full">
      <motion.div
        className="h-full bg-industrial-amber"
        animate={{ width: scanProgress.total > 0
          ? `${(scanProgress.scanned / scanProgress.total) * 100}%`
          : '0%' }}
        transition={{ ease: 'linear', duration: 0.3 }}
      />
    </div>
    <p className="text-[8px] font-mono text-industrial-text-dim truncate text-center">
      {scanProgress.current_file || scanProgress.phase}
    </p>
  </div>
)}
```

Il bottone rimane disabilitato durante la scansione (corretto — non si può analizzare mentre i track vengono re-indicizzati), ma ora l'utente vede chiaramente:
- Il messaggio "Workspace scan in progress — please wait"
- Il contatore `12.450 / 36.701` aggiornato in tempo reale
- Il nome del file corrente in indicizzazione
- La barra amber che avanza
