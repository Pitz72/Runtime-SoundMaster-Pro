## Bug 1 — Scan button bloccato grigio dopo selezione workspace

**Problema**: `handleSelectWorkspace` in `CleanerModule.tsx` chiamava `setIsScanning(true)` prima del `scan_workspace` invoke, ma non chiamava mai `setIsScanning(false)` al completamento con successo. La chiamata esisteva solo nel blocco `catch`. Il listener `scan-progress: complete` in `App.tsx` imposta `setIsScanning(false)`, ma in caso di race condition tra la risoluzione dell'invoke e l'arrivo dell'evento, il bottone restava grigio.

**Fix**: Aggiunta chiamata esplicita `setIsScanning(false)` nel path di successo di `handleSelectWorkspace`, dopo `setLibraryStats`.

```tsx
// Prima (mancante):
const stats = await invoke('get_library_stats');
setLibraryStats(stats as any);
// ← nessun reset di isScanning

// Dopo:
const stats = await invoke('get_library_stats');
setLibraryStats(stats as any);
setIsScanning(false);  // ← aggiunto
```

## Bug 2 — Tutti i file marcati CORRUPT (36.701/36.701)

**Problema**: La funzione `deriveFfprobePath(ffmpegPath)` derivava il percorso di `ffprobe.exe` a partire dal percorso di `ffmpeg.exe`, costruendo un path come `...\binaries\ffprobe.exe`. Questo file non esisteva — solo `ffprobe-x86_64-pc-windows-msvc.exe` è il nome corretto per il sidecar bundled (naming convention Tauri con target triple). La chiamata a `probe_file` falliva immediatamente con `os error 2 — file non trovato`, taggando ogni file come `corrupt`.

**Root cause**: `ffprobe.exe` non era bundled, non dichiarato in `externalBin`, e non aveva un modulo di detection dedicato. La funzione `deriveFfprobePath` era una scorciatoia sbagliata.

**Fix completo**:

1. **Nuovo modulo `src-tauri/src/ffprobe.rs`** — detection ffprobe con stessa architettura di `ffmpeg.rs` e `fpcalc.rs`: bundled → system PATH → common paths per OS.

2. **`src-tauri/src/lib.rs`** — aggiunto `mod ffprobe` e registrato `ffprobe::detect_ffprobe_cmd` nell'invoke handler.

3. **`src-tauri/tauri.conf.json`** — aggiunto `"binaries/ffprobe"` in `externalBin`.

4. **`src/store/appStore.ts`** — aggiunti quattro campi a `SystemStatus`: `ffprobeFound`, `ffprobePath`, `ffprobeVersion`, `ffprobeSource` + relativi valori default nel store iniziale.

5. **`src/App.tsx`** — aggiunta interfaccia `TauriFfprobeInfo`, chiamata `detect_ffprobe_cmd` nel `Promise.all` di inizializzazione, mappatura nel `setSystemStatus`, log di startup (`success` se trovato, `warning` se assente).

6. **`src/components/modules/CleanerModule.tsx`** — rimossa `deriveFfprobePath` e la dipendenza da `useMemo`. `ffprobePath` ora legge direttamente `systemStatus.ffprobePath` — popolato solo se ffprobe è stato rilevato e ha risposto correttamente a `-version`.

7. **Warning UI aggiornato**: il banner "video stream & corrupt checks skipped" ora controlla `!systemStatus.ffprobeFound` invece di `!systemStatus.ffmpegFound`.

**Binario richiesto dall'utente**: copiare `ffprobe.exe` dal pacchetto FFmpeg essentials e rinominarlo in `ffprobe-x86_64-pc-windows-msvc.exe` in `src-tauri/binaries/`. Il file è già presente nel pacchetto gyan.dev scaricato in v0.5.2 (nella cartella `bin/` dello zip).

## Bug 3 — Pulsanti mode switcher "invertiti" (Non-Conform / Duplicates)

**Analisi**: La logica JSX del mode switcher è corretta — `onClick={() => setMode('nonconform')}` sul bottone "Non-Conform", `onClick={() => setMode('duplicates')}` sul bottone "Duplicates", e i blocchi di contenuto gated correttamente su `mode === 'nonconform'` / `mode === 'duplicates'`.

**Causa reale**: Era un artefatto visivo di Bug 1. Con `isScanning` bloccato a `true`, entrambe le modalità mostravano il bottone scan grigio con testo "Scanning workspace..." — contenuto identico che rendeva i due pannelli indistinguibili. Risolto da Bug 1 fix.
