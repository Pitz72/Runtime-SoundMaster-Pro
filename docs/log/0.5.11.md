## Contesto

Audit microscopico dell'intero codice (Rust + React) in preparazione a The Conformer. Emerse 4 criticità gravissime interconnesse attorno al modello workspace del DB, tutte risolte in questa release. Le criticità restanti dell'audit (console flash, stato stale al cambio workspace, esclusione per-gruppo nel resolve, fallback cross-drive) sono pianificate per le prossime release.

---

## Fix 1 — DB multi-workspace contaminato (criticità nota, priorità alta)

**Bug**: `detect_non_conform` e `detect_duplicates` non filtravano per workspace: analizzavano tutti i track mai indicizzati nel DB. Conseguenze: conteggi gonfiati (es. 36.699 file mostrati su un workspace nuovo) e — peggio — quarantena/resolve che spostavano fisicamente file di *altri* workspace dentro `_NonConform`/`_Duplicates` del corrente.

**Fix**: entrambi i comandi ora ricevono `workspace_path` dal frontend e filtrano con `path LIKE ?1 ESCAPE '!'` usando il nuovo helper `workspace_like_prefix`. I record di altri workspace restano nel DB ma non entrano mai più nel ciclo di detection.

## Fix 2 — Guardia destinazione = workspace anche nel backend

**Bug**: il fix v0.5.10 (incidente Genesis) era solo frontend: confronto testuale `selected === workspacePath`, bypassabile su Windows da differenze di maiuscole (`K:\Musica` vs `k:\musica`) o separatori finali. Il backend accettava qualsiasi destinazione.

**Fix**: `quarantine_non_conform_impl` e `resolve_duplicates_impl` confrontano i path **canonicalizzati** (`canonical_or_raw`): se destinazione == workspace l'operazione viene rifiutata con errore esplicito prima di toccare qualsiasi file. In aggiunta, guardia per-file: se un file si trova già dentro la cartella di quarantena, viene aggiornato solo lo status nel DB — mai più rename in place con `_1`.

## Fix 3 — Il rescan non resuscita più i file in quarantena

**Bug**: il reset di isolamento (v0.5.7) riportava a `'unknown'` *anche* i record dentro `_NonConform`/`_Duplicates`. Alla detection successiva quei file venivano ri-flaggati e la ri-quarantena li rinominava in place con `_1` (collisione con se stessi) — un loop di rinomine tra sessioni, stessa famiglia del bug G2 chiuso in v0.5.4.

**Fix**: il reset ora esclude gli status `'non_conform'` e `'duplicate'`: i file in quarantena mantengono il loro stato attraverso i rescan. Se l'utente ripristina manualmente un file dalla quarantena, il vecchio record viene eliminato dalla purga orfani (Fix 4) e il file viene re-indicizzato come nuovo.

## Fix 4 — Purga record orfani a ogni scansione

**Bug**: il DB era solo cumulativo: i record di file cancellati/spostati fuori dall'app restavano per sempre. Al rescan tornavano `'unknown'` e `detect_non_conform` lanciava ffprobe su path inesistenti → flaggati come falsi **corrupt** e proposti per la quarantena.

**Fix**: all'inizio di ogni scansione, i record del workspace il cui file non esiste più su disco vengono eliminati (in transazione). La purga è limitata al workspace corrente: record di altri workspace (potenzialmente su drive non montati) non vengono toccati.

## Fix 7 — Pattern LIKE sicuro (wildcard escapate + separatore)

**Bug**: il reset usava `LIKE '<workspace>%'` grezzo. In SQL `LIKE`, `_` matcha un carattere qualsiasi e `%` qualsiasi sequenza: `K:\Radio_Hits` matchava anche `K:\RadioXHits`. E il prefisso senza separatore finale matchava cartelle sorelle: `C:\Music\Genesis` matchava anche `C:\Music\Genesis2\`.

**Fix**: nuovo helper `workspace_like_prefix()` in `utils.rs` — escapa `%`, `_`, `!` con `ESCAPE '!'` e aggiunge il separatore nativo al prefisso. Usato in tutte le query workspace-scoped (reset, purga, detect non-conform, detect duplicates). Coperto da 5 unit test, inclusi 2 end-to-end contro SQLite reale in-memory.
