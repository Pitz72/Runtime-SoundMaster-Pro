## Fix L2 — Path separator `\\` hardcoded Windows in `CleanerModule.tsx`

### File interessati

- `src/components/modules/CleanerModule.tsx` — costanti `ncDestPath` e `dupDestPath`

### Descrizione del problema

Le due variabili che calcolano il path di default della quarantena usavano `\\` hardcoded come separatore:

```tsx
// PRIMA (Windows-only):
const ncDestPath = customNcDest ?? (workspacePath ? `${workspacePath}\\_NonConform` : null);
const dupDestPath = customDupDest ?? (workspacePath ? `${workspacePath}\\_Duplicates` : null);
```

Il `\\` in un template literal JavaScript è un backslash singolo — il separatore di path di Windows. Su macOS e Linux il separatore corretto è `/`. Sebbene il target primario del progetto sia Windows (operatori radio che usano RadioDJ, MB Studio), il codebase è compilabile su tutte le piattaforme supportate da Tauri, e il path errato avrebbe prodotto una destinazione di quarantena inesistente su sistemi non-Windows.

**Categoria**: cosmetic su Windows, funzionale su macOS/Linux.

### Fix applicato

Rilevamento dinamico del separatore dal workspace path ricevuto dal dialog di sistema Tauri:

```tsx
// DOPO — cross-platform:
const pathSep = workspacePath?.includes('\\') ? '\\' : '/';
const ncDestPath = customNcDest ?? (workspacePath ? `${workspacePath}${pathSep}_NonConform` : null);
const dupDestPath = customDupDest ?? (workspacePath ? `${workspacePath}${pathSep}_Duplicates` : null);
```

**Strategia**: il dialog di sistema (Tauri `open()`) restituisce sempre il path con il separatore nativo del SO. Se il path contiene `\`, il SO è Windows → usa `\`. Altrimenti usa `/` (macOS, Linux). Il rilevamento è robusto perché i path Unix non contengono mai `\` nei path validi.

### Impatto del fix

- Su Windows: comportamento invariato (era già corretto)
- Su macOS/Linux: path di quarantena costruito correttamente con `/`
- Zero dipendenze esterne — nessun import aggiunto

## Fix L3 — `collision_safe_path` duplicata in `cleaner.rs` e `duplicates.rs`

### File interessati

- `src-tauri/src/utils.rs` — **creato**: contiene la funzione canonica
- `src-tauri/src/cleaner.rs` — rimossa la copia locale
- `src-tauri/src/duplicates.rs` — rimossa la copia locale
- `src-tauri/src/lib.rs` — aggiunto `mod utils;`

### Descrizione del problema

La funzione `collision_safe_path` — che genera nomi file non-colliding aggiungendo `_1`, `_2`, ecc. — era definita identicamente in entrambi i moduli:

```rust
// cleaner.rs (riga 501) — copia 1:
fn collision_safe_path(dir: &Path, filename: &str) -> std::path::PathBuf { ... }

// duplicates.rs (riga 578) — copia 2: identica byte per byte
fn collision_safe_path(dir: &Path, filename: &str) -> std::path::PathBuf { ... }
```

**Rischio**: le due copie erano sincronizzate al momento della code review, ma un futuro fix su una non avrebbe automaticamente aggiornato l'altra. Se la logica di naming cambiasse (es. formato `_copy_1` invece di `_1`, o gestione di estensioni composte come `.tar.gz`), la divergenza silente avrebbe prodotto comportamenti asimmetrici tra quarantena non-conform e quarantena duplicati.

### Fix applicato

**Creato `src-tauri/src/utils.rs`** con la funzione canonica:

```rust
/// utils.rs — Utilità condivise tra moduli
/// Runtime SoundMaster Pro — v0.5.6

pub fn collision_safe_path(dir: &Path, filename: &str) -> std::path::PathBuf {
    let candidate = dir.join(filename);
    if !candidate.exists() {
        return candidate;
    }
    let stem = Path::new(filename).file_stem()...;
    let ext = Path::new(filename).extension()...;
    let mut counter = 1u32;
    loop {
        let candidate = dir.join(format!("{stem}_{counter}{ext}"));
        if !candidate.exists() { return candidate; }
        counter += 1;
    }
}
```

**Aggiunto `mod utils;`** in `lib.rs`.

**Importato in entrambi i moduli**:

```rust
// cleaner.rs e duplicates.rs — aggiunto in cima:
use crate::utils::collision_safe_path;
```

**Rimossa la funzione locale** da `cleaner.rs` e `duplicates.rs`.

### Impatto del fix

- Singola fonte di verità per il naming collision-safe
- Futuri aggiornamenti alla logica toccano un solo file
- `cargo check` verifica che entrambi i moduli usino la stessa firma

## Fix L4 — Regex `expect()` in `build_patterns()` → `OnceLock` + panic message migliorato

### File interessati

- `src-tauri/src/cleaner.rs` — `build_patterns()` → `COMPILED_PATTERNS: OnceLock<Vec<Regex>>` + `get_patterns()`

### Descrizione del problema

La versione precedente ricompilava i 17 pattern regex a **ogni invocazione** di `detect_non_conform`:

```rust
// PRIMA — O(17) compilazioni a ogni chiamata:
fn build_patterns() -> Vec<Regex> {
    NON_CONFORM_PATTERNS
        .iter()
        .map(|p| Regex::new(&format!("(?i){}", p)).expect("Invalid regex pattern"))
        .collect()
}

// ... e poi in detect_non_conform_impl:
let patterns = build_patterns();  // ricompila ogni volta
```

**Problema 1 — Performance**: la compilazione regex è computazionalmente costosa (costruisce un automa a stati finiti). Su una libreria da 36.000 file che richiama `detect_non_conform` ripetutamente, questo è lavoro inutile — i pattern sono costanti definite a compile time.

**Problema 2 — `.expect()` opaco**: il panic message `"Invalid regex pattern"` non indica quale dei 17 pattern sia invalido, rendendo il debug difficile. In pratica non può mai esplodere (i pattern sono letterali Rust hardcoded), ma era comunque una bad practice.

### Fix applicato

`OnceLock<Vec<Regex>>` a livello di processo — i pattern vengono compilati al primo accesso e riusati per tutta la vita del processo:

```rust
static COMPILED_PATTERNS: OnceLock<Vec<Regex>> = OnceLock::new();

fn get_patterns() -> &'static [Regex] {
    COMPILED_PATTERNS.get_or_init(|| {
        NON_CONFORM_PATTERNS
            .iter()
            .map(|p| {
                Regex::new(&format!("(?i){p}")).unwrap_or_else(|e| {
                    panic!("BUG: pattern regex non valido '{}': {}", p, e)
                })
            })
            .collect()
    })
}
```

La chiamata in `detect_non_conform_impl` diventa:

```rust
// PRIMA:
let patterns = build_patterns();   // allocazione + compilazione

// DOPO:
let patterns = get_patterns();     // &'static [Regex] — zero allocazione
```

### Miglioramenti ottenuti

| Aspetto | Prima | Dopo |
| --- | --- | --- |
| Compilazione pattern | O(17) per ogni detect | O(17) al primo avvio, poi O(1) |
| Allocazione Vec | Ogni detect | Una sola volta |
| Panic message | `"Invalid regex pattern"` (opaco) | `"BUG: pattern regex non valido '{p}': {e}"` (specifico) |
| Thread safety | N/A (locale) | `OnceLock` — garantita da stdlib |

### Nessuna modifica alla firma pubblica

`detect_non_conform` e `CleanerResult` — invariati. Il frontend non richiede aggiornamenti.

## Fix L5 — Duration fpcalc scartata invece di popolare `tracks.duration_secs`

### File interessati

- `src-tauri/src/duplicates.rs` — Phase 3 acoustic fingerprint loop

### Descrizione del problema

La funzione `run_fpcalc` restituisce una tupla `(fingerprint: String, duration: f64)`. Il secondo elemento — la durata in secondi calcolata da Chromaprint decodificando il file audio — veniva sistematicamente ignorato:

```rust
// PRIMA — _dur scartato:
if let Some((fp, _dur)) = run_fpcalc(&t.path, fpcalc_bin) {
    let _ = conn.execute(
        "UPDATE tracks SET fingerprint = ?1 WHERE id = ?2",
        rusqlite::params![fp, t.id],
    );
    // _dur: ignorato silenziosamente
}
```

**Contesto**: `tracks.duration_secs` viene popolato tipicamente dallo scanner (dai tag ID3 via FFprobe). Ma esistono tre scenari in cui un track raggiunge la Phase 3 con `duration_secs IS NULL`:

1. **File senza tag ID3**: MP3 raw senza header, file audio prodotti da encoding non standard
2. **FFprobe non disponibile**: il sistema è configurato senza ffprobe (es. installazione minimale)
3. **File con metadati corrotti**: FFprobe ha estratto stream ma non ha trovato duration

In tutti questi casi, fpcalc fornisce una duration affidabile (la calcola decodificando l'audio reale, non leggendo i tag). Non usarla lasciava `duration_secs = NULL` nel DB, degradando il best-pick algorithm nella risoluzione duplicati (che usa `duration_secs` come terzo criterio di selezione).

### Fix applicato

```rust
// DOPO — dur usato per popolare il DB se il campo è assente:
if let Some((fp, dur)) = run_fpcalc(&t.path, fpcalc_bin) {
    let _ = conn.execute(
        "UPDATE tracks SET fingerprint = ?1 WHERE id = ?2",
        rusqlite::params![fp, t.id],
    );

    // Popola duration_secs se assente nel DB.
    // Condizione: t.duration_secs.is_none() (il track non ha duration caricata in memoria)
    // AND dur > 0.0 (fpcalc ha prodotto un valore sensato)
    // AND duration_secs IS NULL (double-check nel DB — protezione da race condition)
    if t.duration_secs.is_none() && dur > 0.0 {
        let _ = conn.execute(
            "UPDATE tracks SET duration_secs = ?1 WHERE id = ?2 AND duration_secs IS NULL",
            rusqlite::params![dur, t.id],
        );
    }

    let key = fp.chars().take(120).collect::<String>();
    by_fingerprint.entry(key).or_default().push(t.id);
}
```

**Doppia guardia `AND duration_secs IS NULL`**: anche se `t.duration_secs` era None al momento della query iniziale, un'altra sessione concorrente potrebbe aver scritto il valore nel frattempo. La condizione SQL garantisce che l'UPDATE sia idempotente e non sovrascriva mai una duration già presente (es. da FFprobe).

### Impatto del fix

- I track fingerprinted da fpcalc ora hanno `duration_secs` popolato nel DB
- Il best-pick algorithm usa il terzo criterio (durata) correttamente anche per track senza tag
- La Column `duration_secs` è ora più densa nel DB: meno NULL, più dati utili
- Zero regression: la condizione `AND duration_secs IS NULL` preserva duration esistenti
