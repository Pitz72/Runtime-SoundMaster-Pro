## Obiettivo di questa versione

Il v0.2.0 aveva una UI completa ma completamente disconnessa dal backend — nessun dato reale fluiva da Rust a React, le statistiche mostravano `—`, nessuna scansione era possibile. Il v0.3.0 implementa il **Layer 0 dell'infrastruttura condivisa**, il prerequisito di tutti i moduli operativi (Cleaner, Conformer, Librarian).

Dopo questa versione l'utente può:

1. Selezionare una cartella workspace dall'Hub
2. Avviare una scansione ricorsiva della libreria audio
3. Vedere il progresso in real-time (file per file, progress bar)
4. Vedere le statistiche aggiornate nell'Hub (Total Assets, Duplicates, Anomalies) con dati reali dal database SQLite

### `src-tauri/src/db.rs`

**Aggiunto**: `LibraryStats` struct + `get_library_stats` comando Tauri.

```rust
pub struct LibraryStats {
    pub total_tracks: i64,  // COUNT(*) da tracks
    pub non_conform: i64,   // conforming_status = 'non_conform'
    pub duplicates: i64,    // conforming_status = 'duplicate'
    pub to_verify: i64,     // conforming_status = 'to_verify'
}
```

Il comando apre una connessione read-only dedicata per le query aggregate — sicuro in WAL mode dove lettori multipli non si bloccano con il writer dello scanner. Ogni query usa `query_row` con `.unwrap_or(0)` per robustezza contro DB vuoto o prima scansione.

**Valori al primo avvio** (prima di qualsiasi scansione): tutti 0 — corretto e atteso. `non_conform` e `duplicates` resteranno a 0 fino a quando The Cleaner (v0.4.0/v0.5.0) eseguirà la propria analisi.

### `src-tauri/src/scanner.rs` *(nuovo)*

Modulo completo di scansione workspace. Struttura principale:

#### `ScanProgress` (evento Tauri `"scan-progress"`)

```rust
pub struct ScanProgress {
    pub scanned: u64,        // file processati finora
    pub total: u64,          // totale file audio trovati (0 durante discovery)
    pub current_file: String, // nome file corrente
    pub phase: String,       // "discovering" | "indexing" | "complete" | "error"
}
```

#### `ScanResult` (valore di ritorno del comando)

```rust
pub struct ScanResult {
    pub scan_id: i64,       // ID del record in tabella scans
    pub total_files: u64,
    pub duration_secs: f64,
}
```

#### Pipeline di scansione (`scan_workspace_impl`)

**Fase 1 — Discovery**: raccolta ricorsiva di tutti i path audio via `WalkDir`. Il filtraggio avviene sull'estensione (lowercase): `mp3 | flac | wav | m4a | aac | ogg | wma`. Segue i symlink (`follow_links(true)`). La lista risultante contiene solo `PathBuf` — nessun contenuto file in RAM.

**Fase 2 — Indicizzazione DB-First**: per ogni file trovato, esegue `INSERT OR IGNORE INTO tracks` con i dati ricavabili senza aprire il file audio (path, filename, format, file_size_bytes). I metadati audio completi (bitrate, sample_rate, artist, title, ecc.) saranno estratti nei moduli operativi successivi.

Dettagli implementativi:

- Lo statement SQL è preparato **una sola volta fuori dal loop** (`conn.prepare()`) per evitare overhead di parsing ripetuto su librerie grandi.
- `INSERT OR IGNORE` su `path UNIQUE`: le rescansioni incrementali saltano i file già indicizzati senza errori.
- Il campo `conforming_status` viene impostato a `'unknown'` (default schema) — verrà aggiornato da The Cleaner.
- Ogni file inserito riceve `scan_id` per tracciabilità della sessione di scansione.
- Progress event emesso ogni **100 file** o sull'ultimo — bilanciamento tra granularità del feedback e overhead IPC Tauri. Su una libreria da 50.000 file produce ~500 eventi, un carico IPC accettabile.

**Record sessione scansione**: all'inizio viene creato un record in tabella `scans` con `status='running'`; alla fine viene aggiornato a `status='completed'` con `total_files` e `finished_at`. Questo fornisce storico delle scansioni consultabile dal Librarian (Fase futura).

#### `scan_workspace` (comando Tauri async)

L'operazione è avvolta in `tokio::task::spawn_blocking`: `walkdir` e `rusqlite` sono API sincrone bloccanti, non adatte a essere eseguite direttamente in un future async. `spawn_blocking` le sposta su un thread del pool Tokio dedicato alle operazioni bloccanti, senza congelare il runtime async principale.

`AppHandle` è `Send + 'static` in Tauri 2 — sicuro da passare nella closure del thread per l'emissione degli eventi di progresso.

.setup(|app| {

### `src/App.tsx`

**Nuovi import**: `invoke` da `@tauri-apps/api/core`, `listen` da `@tauri-apps/api/event`.

**Fetch stats post-init**: dopo l'inizializzazione Tauri, viene invocato `get_library_stats` e il risultato viene scritto nello store. Se la libreria contiene già tracce indicizzate (riavvio app con DB esistente), l'Hub mostra immediatamente i conteggi reali.

**Listener globale `"scan-progress"`** registrato al mount di App, deregistrato all'unmount:

- Ad ogni evento: aggiorna `scanProgress` nello store.
- Su `phase === 'complete'`: imposta `isScanning = false`, azzera `scanProgress`, invoca `get_library_stats` per aggiornare i contatori (il ciclo completo: scan → evento complete → refresh stats → UI aggiornata).
- Su `phase === 'error'`: reset dello stato scanning.

Il listener è in `App.tsx` (non in `HubModule`) perché deve restare attivo indipendentemente dal modulo corrente — una scansione avviata dall'Hub deve completare anche se l'utente naviga altrove.

### `src/components/modules/HubModule.tsx`

**Nuovi import**: `invoke` da `@tauri-apps/api/core`, `ScanResult` da store.

**Store reads aggiunti**: `libraryStats`, `isScanning`, `scanProgress`, `setIsScanning`.

**`handleSelectWorkspace` aggiornato**:

1. Apre dialog nativa (invariato).
2. Se path selezionato: `setWorkspacePath` + `setIsScanning(true)`.
3. `await invoke<ScanResult>('scan_workspace', { path })` — attende il completamento.
4. Log del risultato finale con durata e totale file.
5. In `finally`: `setIsScanning(false)` (anche su errore).

Il bottone workspace è disabilitato durante `isScanning` per prevenire scansioni concorrenti.

**UI progress inline nell'hero**: visibile solo durante `isScanning && scanProgress`. Composta da:

- Riga di testo: nome file corrente a sinistra, contatore `scanned / total` a destra.
- Barra di progresso `motion.div` con larghezza animata (`ease: 'linear'`). Durante la fase "discovering" (total = 0) la barra è piena — indica attività senza percentuale.

**Stats grid cablate a `libraryStats`**:

- `Total Assets` → `libraryStats.total_tracks`
- `Duplicates Detected` → `libraryStats.duplicates` (0 fino a The Cleaner)
- `Anomalies Detected` → `libraryStats.non_conform` (0 fino a The Cleaner)
- Valore fallback `—` quando `libraryStats === null` (prima del caricamento)

## Flusso end-to-end v0.3.0

```text
Utente clicca "Select Workspace"
  → open() dialog nativa Tauri
  → setWorkspacePath(path)
  → setIsScanning(true)
  → invoke('scan_workspace', { path })  ← async, ritorna solo al termine

  [Backend Rust — thread spawn_blocking]
    INSERT INTO scans (root_path, 'running')
    WalkDir ricorsivo → filtra estensioni audio
    emit('scan-progress', { phase: 'discovering' })
    Per ogni file:
      INSERT OR IGNORE INTO tracks (path, filename, format, size, scan_id)
      ogni 100 file: emit('scan-progress', { scanned, total, filename, 'indexing' })
    UPDATE scans SET status='completed'
    emit('scan-progress', { phase: 'complete' })
    return ScanResult { scan_id, total_files, duration_secs }

  [Frontend — listener in App.tsx]
    ogni evento 'scan-progress' → setScanProgress() → HubModule aggiorna barra
    su phase='complete':
      setIsScanning(false)
      invoke('get_library_stats') → setLibraryStats()
      → HubModule mostra contatori reali

  invoke ritorna → HubModule logga durata e totale file
```

## Prossimo Step — v0.4.0: The Cleaner — Non-Conform Detection

Con il workspace scanner funzionante e il DB popolato, il prossimo passo è il **primo modulo operativo reale**:

- Lettura dei `tracks` con `conforming_status = 'unknown'` dal DB
- Analisi del nome file: regex pattern YouTube (`(Official Video)`, `[Lyrics]`, ID YouTube, ecc.)
- FFprobe probe per rilevare file video mascherati da audio
- Rilevamento file corrotti (durata = 0 o FFprobe fallisce)
- Spostamento file in `_NonConform/` (operazione non-distruttiva)
- Aggiornamento `conforming_status = 'non_conform'` nel DB
- Refresh stats Hub → counter "Anomalies" si popola con dati reali
- Wiring CleanerModule: la step 1 "SCAN" avvia il processo reale, step 2 "REVIEW" mostra i file trovati
