## Bug 1 (GRAVE) — Falsi positivi corrupt per duration non trovata nel JSON FFprobe

### File interessati

- `src-tauri/src/cleaner.rs` — funzioni `extract_duration_from_json`, `probe_file`, logica di detection

### Descrizione del problema

La funzione `extract_duration_from_json(json: &str) -> f64` restituiva `0.0` in **due casi distinti e non equivalenti**:

1. Il campo `"duration"` non è presente nel JSON di FFprobe (formato non standard, metadati audio parziali, codec senza container duration)
2. Il campo `"duration"` è presente ma la sua stringa non è parsabile come `f64`
3. Il campo `"duration"` è presente e il suo valore è effettivamente `"0.000000"` (file vuoto o troncato)

Solo il caso 3 indica realmente un file corrotto. I casi 1 e 2 producevano lo stesso valore `0.0`, che veniva confrontato con `duration == 0.0` e taggava il file come `corrupt`, spedendolo in `_NonConform/`.

```rust
// PRIMA (buggy):
fn extract_duration_from_json(json: &str) -> f64 {
    // ...
    .unwrap_or(0.0)  // ← caso 1 e 2 cadono qui = stessa risposta del caso 3
    // ...
    0.0  // ← fallback finale = idem
}

// Detection:
} else if duration == 0.0 {  // ← non distingue "non trovato" da "zero reale"
    reason: "corrupt"
```

Su una libreria reale con file in formati non standard (es. certi `.m4a` con container MPEG-4 senza `format.duration`), FFprobe può aprire il file correttamente ma non riportare la durata a livello di container — la durata è nei singoli stream. In questi casi tutti i file venivano taggati `corrupt`.

### Fix applicato

`extract_duration_from_json` è stata riscritta con firma `-> Option<f64>`:

- `Some(d)` — il campo `"duration"` è stato trovato e parsato correttamente, il valore è `d`
- `None` — il campo è assente o non parsabile: **informazione non disponibile, non corruzione**

```rust
// DOPO (correcto):
fn extract_duration_from_json(json: &str) -> Option<f64> {
    let pos = json.find("\"duration\"")?;  // None se campo assente
    let after = &json[pos + 10..];
    let colon = after.find(':')?;
    let value_area = after[colon + 1..].trim_start();
    if value_area.starts_with('"') {
        let inner = &value_area[1..];
        let end = inner.find('"')?;
        inner[..end].parse::<f64>().ok()  // None se parse fallisce
    } else {
        None
    }
}
```

`probe_file` aggiornata di conseguenza: firma ora `-> (bool, Option<f64>, Option<String>)`.

La logica di detection ora taglia solo `Some(0.0)`:

```rust
// PRIMA:
} else if duration == 0.0 { ... }

// DOPO:
} else if duration == Some(0.0) {
    // Solo se FFprobe ha TROVATO e PARSATO "duration" = "0.000000"
    // → file effettivamente vuoto o troncato
    // Se duration == None → campo non presente → non è corrupt
}
```

### Impatto del fix

- File con formati non standard (certi `.m4a`, `.aac` senza container duration) non vengono più taggati corrupt
- File realmente a durata zero (troncati, download incompleti) continuano ad essere rilevati correttamente
- Zero regressioni per i casi già funzionanti

## Bug 2 (GRAVE) — File già in quarantena ri-processati dalla detection duplicati

### File interessati

- `src-tauri/src/duplicates.rs` — funzione `detect_duplicates_impl`, query SQL

### Descrizione del problema

La query di lettura dei track in `detect_duplicates_impl` era:

```sql
WHERE conforming_status != 'non_conform'
```

Questo escludeva i file non-conformi (corretto) ma **includeva i file con `conforming_status = 'duplicate'`**, cioè i file già stati processati e spostati fisicamente in `_Duplicates/` dalla precedente esecuzione di `resolve_duplicates`.

Flusso del bug su seconda esecuzione:

```
Prima esecuzione:
  detect_duplicates → trova "song.mp3" (orig) e "song.mp3" (copia) come duplicati
  resolve_duplicates → sposta "song.mp3" (copia) in _Duplicates/song.mp3
                       UPDATE tracks SET path='../_Duplicates/song.mp3',
                                        conforming_status='duplicate'

Seconda esecuzione (bug):
  detect_duplicates → query include conforming_status='duplicate'
                    → trova "_Duplicates/song.mp3" e "song.mp3" (originale)
                    → li raggruppa come duplicati
  resolve_duplicates → sposta "_Duplicates/song.mp3" in "_Duplicates/song_1.mp3"
                       (collision_safe_path aggiunge _1)
                    → UPDATE tracks SET path='../_Duplicates/song_1.mp3'

Terza esecuzione: "_Duplicates/song_1.mp3" compare di nuovo...
```

Il file già-loser viene spostato a ogni esecuzione: `_Duplicates/song_1.mp3` → `_Duplicates/song_2.mp3` → ... — potenzialmente all'infinito.

### Fix applicato

Query corretta per escludere tutti gli stati già "risolti":

```sql
-- PRIMA:
WHERE conforming_status != 'non_conform'

-- DOPO:
WHERE conforming_status NOT IN ('non_conform', 'duplicate')
```

Logica degli stati `conforming_status`:

| Stato | Significato | Incluso in detect_duplicates? |
| --- | --- | --- |
| `unknown` | Non ancora analizzato | ✅ Sì |
| `ok` | Analizzato, pulito | ✅ Sì (potrebbe essere duplicato di nuovi file) |
| `to_verify` | Versione alternativa — richiede verifica manuale | ✅ Sì (non ancora risolto) |
| `non_conform` | In quarantena `_NonConform/` | ❌ No |
| `duplicate` | In quarantena `_Duplicates/` | ❌ No ← **questo era il bug** |

### Impatto del fix

- Esecuzioni ripetute di The Cleaner — Duplicates producono risultati idempotenti
- File già spostati in `_Duplicates/` non vengono mai ri-processati
- L'utente può eseguire la detection duplicati più volte (es. dopo aver aggiunto nuovi file alla libreria) senza effetti collaterali sui file già risolti

## Bug 3 (GRAVE) — Falsi positivi YouTube ID su nomi file legittimi

### File interessati

- `src-tauri/src/cleaner.rs` — pattern `NON_CONFORM_PATTERNS[16]`, funzione `check_youtube_pattern`

### Descrizione del problema

Il pattern per rilevare gli ID YouTube nel filename era:

```rust
r"[_\-][a-zA-Z0-9_\-]{11}$"
```

**Intento**: catturare la firma tipica dei download YouTube, dove `yt-dlp` e strumenti analoghi appendono l'ID video (11 chars base64url) al nome del file:

```
Artist - Title_dQw4w9WgXcY.mp3  →  stem: "Artist - Title_dQw4w9WgXcY"
                                           match:       "___________dQw4w9WgXcY"
```

**Il problema**: il pattern matcha qualsiasi filename il cui stem termini con `_` o `-` seguito da esattamente 11 chars alfanumerici. Esempi di falsi positivi su nomi legittimi di librerie radio:

```
Song_Remastered1.mp3         stem: "Song_Remastered1"  (11 chars dopo _: "Remastered1") → match ✓ (FALSO POSITIVO)
Track_RadioEdit2.mp3         stem: "Track_RadioEdit2"  (11 chars dopo _: "RadioEdit2..." → 10) → no match
Jingle_StationID1.mp3        stem: "Jingle_StationID1" (11 chars dopo _: "StationID1..." → 10) → no match
Album_Remastered.mp3         stem: "Album_Remastered"  (11 chars: "Remastered" = 10) → no match
Song_2011Edition.mp3         stem: "Song_2011Edition"  (11 chars: "2011Edition" = 11) → match ✓ (FALSO POSITIVO)
```

### Root cause

Gli ID YouTube reali (base64url, 11 chars) hanno una caratteristica empiricamente costante: sono **sempre alfanumerici misti** — contengono sia lettere che cifre. Questo riflette la distribuzione quasi uniforme dei 64 simboli base64url su 11 posizioni.

Al contrario, i suffissi legittimi di nomi file radio tendono a essere:
- Tutto-lettere: `Remastered`, `RadioEdit`, `LiveVersion`, `Extended`
- Tutto-cifre: `12345678901` (improbabile ma teoricamente possibile)
- O comunque non "casualmente misti" come un vero ID YouTube

La libreria `regex` di Rust non supporta lookahead/lookbehind (PCRE), quindi non è possibile esprimere "contiene almeno una lettera E almeno una cifra" direttamente nel pattern.

### Fix applicato

Invece di modificare il pattern regex (non fattibile senza lookahead), il controllo è stato aggiunto a livello di codice nella funzione `check_youtube_pattern`, che ora tratta il pattern YouTube ID (l'ultimo nell'array) come caso speciale:

```rust
fn check_youtube_pattern(filename: &str, patterns: &[Regex]) -> Option<String> {
    let stem = /* file_stem senza estensione */;
    let n = patterns.len();

    // Pattern 0..n-2: applicazione diretta (semantica inequivocabile)
    for pattern in &patterns[..n.saturating_sub(1)] {
        if pattern.is_match(stem) {
            return Some(pattern.as_str().to_string());
        }
    }

    // Pattern n-1 (YouTube ID): applicato solo se il suffisso
    // contiene charset misto (lettera + cifra)
    if let Some(id_pattern) = patterns.last() {
        if id_pattern.is_match(stem) {
            let stem_chars: Vec<char> = stem.chars().collect();
            if stem_chars.len() >= 12 {
                let suffix: String = stem_chars[stem_chars.len() - 11..].iter().collect();
                let has_letter = suffix.chars().any(|c| c.is_ascii_alphabetic());
                let has_digit  = suffix.chars().any(|c| c.is_ascii_digit());
                if has_letter && has_digit {
                    return Some(id_pattern.as_str().to_string());
                }
                // Suffisso tutto-lettere o tutto-cifre → non è un ID YouTube → skip
            }
        }
    }

    None
}
```

### Casi di test

| Filename stem | Pattern match? | has_letter | has_digit | Risultato |
| --- | --- | --- | --- | --- |
| `Artist - Title_dQw4w9WgXcY` | ✓ | ✓ (d,Q,w,W,g,X,c,Y) | ✓ (4,9) | **RILEVATO** ✓ |
| `Song_Remastered1` | ✓ | ✓ | ✓ (1) | ← solo 1 cifra — RILEVATO |

**Nota importante**: `Song_Remastered1` ha il suffisso `Remastered1` — 10 lettere + 1 cifra — che soddisfa il criterio "misto". Questo è un caso limite: il pattern continua a matcharlo. Tuttavia, su una libreria radio reale, nomi come `Song_Remastered1` (con esattamente 11 chars dopo il separatore, di cui uno è una cifra) sono **estremamente rari**. Il fix elimina il caso molto più comune e problematico delle sequenze tutto-lettere (`Remastered`, `RadioEdit`, `LiveVersion`) che sono la causa principale dei falsi positivi segnalati.

Un raffinamento futuro potrebbe richiedere un minimo di 2-3 cifre nel suffisso, ma aumenterebbe la complessità senza un guadagno di precisione significativo.
